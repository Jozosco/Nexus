## 1. customs-gw — `resultCode=99` (A-101)

### 조정자 지적이 정확했다 — 직전 세션의 최적화가 틀렸다

```
[경고] 1511/US/2010~2026: resultCode=99 시작과 종료의 조회기간은 1년이내 기간만 가능합니다.
```

A-094에서 "API가 `strtYymm~endYymm` 다월 범위를 지원하므로 연도 루프가 불필요하다"고
판단해 호출을 1,530회 → 90회로 줄였다. **이 전제가 틀렸다.** API는 다월 범위를 지원하되
**1년 이내로 제한**한다. 문서에 명시되지 않아 실행으로만 확인 가능한 제약이었다.

추가로 이 오류는 **조용히 실패**했다. `_request()`가 `resultCode != "00"`일 때 빈 리스트를
반환했고, 상위 `fetch_range()`는 그것을 "데이터 없음"으로 해석해 폴백을 하지 않았다.
로그의 `[정보] Palm Oil (1511)/U.S.A: 데이터 없음`이 그 결과다 — **실제로는 요청 자체가
거부된 것**인데 데이터가 없는 것처럼 보였다.

### 조치 — 연 단위 복귀 + 병렬화로 시간 문제 해결

호출량을 줄일 수 없다면(1,530회 고정), **벽시계 시간**을 줄이는 방법은 동시성뿐이다.

| 항목 | 조치 |
|---|---|
| 요청 단위 | `{YYYY}01 ~ {YYYY}12`(정확히 12개월, 1년 이내 제약 충족) |
| 동시성 | `ThreadPoolExecutor(max_workers=5)` — 연도 단위 병렬 (`CUSTOMS_MAX_WORKERS`로 조정) |
| 커넥션 풀 | max_connections 12 / keepalive 8 (워커 수 이상 확보) |
| 타임아웃 | connect 10s / read 30s (A-094 유지) |
| 재시도 | 3회 지수 백오프 (A-094 유지) |
| 시간 예산 | 3시간 초과 시 수집분 저장 후 정상 종료 (A-094 유지) |
| 잡 상한 | `timeout-minutes: 240` (A-094 유지) |

**예상 소요**: 1,530회 ÷ 동시 5 × (응답 2~4초) ≈ **15~25분**.

### 조정자 질문에 대한 답 — "수집 시작·종료 연도 조정으로 해결되나?"

**아니오. 연도 범위를 줄이는 것은 해결책이 아니라 데이터 축소입니다.** 2010~2011로 좁히면
오류는 사라지지만 15개년 분석창(M-008)을 포기하게 됩니다. 위 병렬화로 **2010~2026 전 구간을
유지한 채** 시간 문제를 해결했으므로, `start_year=2010 / end_year=2026`으로 실행하시면 됩니다.

## 2. Databento — `price_date`가 전부 1970-01-01 (A-102)

### 근본원인 — 로컬에서 100% 재현 완료

```python
pd.concat(parts, ignore_index=True)   # ← 각 청크의 ts_event DatetimeIndex를 폐기
df.reset_index()                       # ← RangeIndex(0,1,2…)가 'index' 컬럼이 됨
pd.to_datetime([0,1,2,…], utc=True)    # ← 정수를 **에폭 나노초**로 해석
# 결과: 1970-01-01 00:00:00.000000000, .000000001, .000000002 …
```

재현 결과가 관측 증상과 정확히 일치한다:

| 증상 | 설명 |
|---|---|
| `기간: 1970-01-01 ~ 1970-01-01` | 모든 값이 1970-01-01 당일 (나노초 단위로만 차이) |
| `4,051 거래일`(nunique) | 나노초가 행마다 달라 고유값은 행 수와 같음 |
| `20,255행` = 4,051 × 5 | 지표 5종(OHLCV) × 4,051행 — 행 수 자체는 정상 |

즉 **데이터는 정상 수신됐고 날짜 컬럼만 파괴**된 것이다. 2010~2026 거래일이 약 4,032일이므로
4,051은 오히려 정상 범위다. "누락 데이터"로 보인 것은 일부 연도 청크 실패와 날짜 파괴가
겹쳐 연도별 분포를 확인할 수 없었기 때문이다.

### 조치

1. **`_to_price_date()` 신설** — concat **이전에** 청크별로 시각을 컬럼으로 승격.
   `DatetimeIndex`면 이름이 없어도 사용하고, 아니면 `ts_event/ts_recv/date/time`을 찾는다.
   **셋 다 없으면 즉시 예외** — 임의 컬럼 추정(1970 오염의 원인)을 금지한다.
2. **`_assert_date_range()` 신설** — 결과가 요청 구간 밖이면 저장하지 않고 실패시킨다.
   조용한 오염을 즉시 드러내는 안전장치.
3. **`yyyy-mm-dd` 저장**(조정자 요청) — 일봉이므로 시각 성분을 제거하고 CSV·XLSX에
   `%Y-%m-%d` 문자열로 기록.
4. **연도별 커버리지 리포트** — `[커버리지] 연도별 거래일: {...}` + 200일 미만 연도 경고.
   "누락 데이터"를 눈으로 확인할 수 있게 한다.

### 로컬 검증 결과

```
[검증] 기간 정합 OK: 2010-01-01 ~ 2011-12-16
price_date 샘플: ['2010-01-01', '2010-01-04']     ← yyyy-mm-dd
연도별: {2010: 250, 2011: 250}
1970 오염: 0건
무명 DatetimeIndex 처리: 2012-01-02 ~ 2012-12-14  ← 인덱스명 없어도 정상
시각 컬럼 부재 시: 즉시 중단(ValueError)          ← 조용한 오염 차단
```

## 3. USDA PSD — `TypeError: _get_retry() got an unexpected keyword argument 'headers'` (A-103)

세션 45에서 PSD 폴백 체인을 넣으며 `_get_retry(_u, headers=_h, ...)`로 호출했으나,
헬퍼 시그니처는 `(url, params=None, timeout=60, tries=4)`로 `headers`를 받지 않았다.
**내가 만든 회귀**다. 헬퍼가 워크플로우 heredoc에 **9벌 복제**돼 있어 한 곳만 고치면
놓치기 쉬운 구조였다 — 9곳 전부 `headers` 파라미터를 추가하고 `c.get()`에 전달했다.

부수적으로 로그의 `[경고] PSD https:/`는 라벨 생성 시 `url.split('/api')[0]`이
`https://api...`의 `//api`에 먼저 매칭돼 생긴 표기 오류다(진단에 영향 없음).

## 4. BOK ECOS — ConnectTimeout 신규 발생 (A-104)

KOSIS·관세청은 해소됐는데 BOK에서 같은 증상이 나타났다. 이는 개별 호스트 문제가 아니라
**한국 공공기관 호스트 계열의 공통 취약성**이며, 완화가 호스트마다 따로 필요했음을 뜻한다.

근본 처방은 **재시도 로직의 일원화**다. `_get_retry`가 9벌 복제돼 있어 개선이 한 곳에
반영되지 않는 구조가 문제를 키웠다(장애 3과 같은 뿌리).

### `scripts/http_kr.py` 신설

| 기법 | 목적 |
|---|---|
| 다중 전송 경로 (IPv4 강제 → 기본) | IPv6 블랙홀 회피 |
| **https ↔ http 스킴 폴백** | 일부 기관은 평문 경로가 더 안정적 |
| 지터 백오프(5→30s + 무작위 2.5s) | 동시 재시도 몰림에 의한 레이트리밋 유발 방지 |
| 5회 재시도 | 간헐 장애 흡수 |
| 계층 진단 메시지 | 실패 시 DNS 성공 여부·시도 패턴을 함께 출력 |

BOK 점검은 **비치명 처리**한다 — 원/달러 환율은 FRED `DEXKOUS`로 대체 수집이 가능하므로
파이프라인 차단 사유가 아니다.

## 5. Trading Economics — HTTP 409 스로틀 (A-105)

### 근본원인: 실패 처리가 스로틀을 자초하는 구조

```python
try:
    data = te.getMarketsBySymbol(symbols="bdi")   # 1차: 가벼움
except Exception as e:
    data = te.getMarketsData(marketsField="commodities")   # 2차: 전체 상품 목록(무거움)
```

1차가 실패하면 **대기 없이 즉시** 훨씬 무거운 2차 호출을 던진다. 이전 세션에서
"BDI 발견 (심볼 재확인 필요)"가 나온 것은 이미 이 2차 경로를 타고 있었다는 뜻이다.
호출이 누적되면서 구독 등급 한도를 넘겨 **409 `Please slow down`**로 전환된 것이다.

### 조치

- 호출을 **1회로 축소**(2차 전체 목록 조회 제거)
- 409/429/`slow down`/`throttle` 감지 시 **지수 백오프 30s → 60s → 120s** 재시도
- 레이트리밋이 아닌 오류는 재시도하지 않음(동일 결과)
- 최종 실패해도 **비치명** — BDI는 9개년 수동 업로드(`TE_BDI`)로 이미 커버됨

## 6. USDA ARMS — `recordCount: 0` (A-106)

응답이 `{'status': 'ok', 'total': {'recordCount': 0}}`이므로 **API는 정상이고 쿼리 조합에
데이터가 없는 것**이다(장애 3과 원인이 다르다 — 그쪽은 우리 코드의 TypeError).

파라미터를 추측으로 고치는 대신 **메타데이터 엔드포인트로 유효값을 먼저 조회**하도록 바꿨다:
`/data/arms/year` · `/state` · `/report` · `/category` · `/farmtype`을 순회해 실제 허용값을
로그에 출력한다. 다음 실행 로그를 보면 어떤 값이 유효한지 확정할 수 있고, 그때 쿼리를
정확히 맞추면 된다. **외부 문의 없이 자체 해결 가능**하다.

대두 생산비용은 G1 핵심 8변수에 포함되지 않는 보조 지표이므로 비치명 유지.

## 7. Open-Meteo / climate_connector — 12개 지역 동시 수집 (A-107)

### 조정자 질문: "12개 지역을 동시에 수집할 수 있는가?"

**구조적으로는 가능하나, 심각한 잠재 결함이 있었다.**

| 항목 | 확인 결과 |
|---|---|
| 등록 지역 | **12개** — 중국 3(헤이룽장·산둥·장쑤) · 미국 3(일리노이·아이오와·인디애나) · 브라질 3(마투그로수·파라나·마투그로수두술) · 아르헨티나 3(코르도바·산타페·부에노스아이레스) |
| 수집 변수 | 8종(최고·최저기온, 강수, 일사, 토양온도, 토양수분, 증발산, 일조시간) |
| 호출 방식 | 지역별 순차 1회 + 0.3초 간격 — 레이트리밋 관점에서 문제 없음 |
| 오류 처리 | 지역별 try/except로 부분 실패 허용 |

**발견한 결함 3가지**:

1. **[심각] 변수 1개가 전 지역을 죽인다** — Open-Meteo는 daily 집계로 지원되지 않는 변수가
   하나라도 섞이면 **HTTP 400**을 반환한다. 현재 코드는 8개 변수를 한 번에 요청하므로,
   API 사양이 바뀌어 한 변수가 빠지면 **12개 지역 전부**가 실패한다. 그런데 실패는
   `[경고]`로만 찍히고 잡은 성공으로 끝나 **조용한 전면 실패**가 된다.
2. **[중] 부분 실패가 드러나지 않는다** — 12개 중 3개만 성공해도 최종 로그는
   "총 N건 (3개 지역)"으로만 나와, 9개가 빠진 사실이 눈에 띄지 않는다.
3. **[중] 분석창 불일치** — `run(start_year=2017)`로 하드코딩돼 있어 2010~ 분석창(M-008)과
   맞지 않는다. 백필 워크플로우가 `HISTORICAL_START_YEAR=2010`을 주입해도 무시된다.

### 조치

1. **유효 변수 자동 확정** — 짧은 구간(3일)으로 전체 변수를 프로브하고, 400이면 변수를
   하나씩 확인해 지원되는 집합만 남긴다. 제외된 변수는 로그에 명시한다.
2. **12/12 명시 리포트** — `[집계] 지역 수집 N/12 · 실패: ...` + 지역별 일수 딕셔너리 출력.
3. **`HISTORICAL_START_YEAR` 반영** — 기본값 2010.

> ⚠️ **샌드박스 제약**: 개발 환경 프록시가 `archive-api.open-meteo.com`을 차단(403)해
> 실측 검증을 하지 못했다. 위 조치는 코드 검토 기반이며, **Actions 실행 로그의
> `[집계] 지역 수집 N/12`로 최종 확인**이 필요하다.
