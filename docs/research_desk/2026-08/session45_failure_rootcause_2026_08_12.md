## 1. customs-gw — 6시간 초과 (A-094)

### 근본원인 (정량 확인)

호출 구조가 `9품목 × 10국가 × 17연도 = 1,530회`였고, 실패 1건당 최악 소요가
`4회 재시도 × 60초 + 백오프 14초 = 254초`였다. 실패율별 총 소요는 다음과 같다.

| 실패율 | 총 소요 | 6시간 초과 |
|---|---|---|
| 5% | 5.9시간 | 아니오(경계) |
| 10% | 11.3시간 | **예** |
| 20% | 22.0시간 | **예** |

즉 **10% 남짓만 실패해도 6시간을 넘기는 구조**였다. "데이터가 작은데 왜 6시간인가"의 답은
데이터 크기가 아니라 **연결 실패 대기 시간의 누적**이다. 추가로 호출마다 `httpx.Client`를
새로 만들어 TCP·TLS 핸드셰이크를 1,530회 반복하고 소켓을 닫지 않았다.

### 조치 (API 우선)

1. **다년 범위 단일 호출**: API가 `strtYymm~endYymm` 다월 범위를 지원하므로 연도 루프가
   불필요했다. `(HS·국가)`당 1회로 **1,530 → 90회(17배 감소)**. 범위 조회 실패 시에만
   연도 분할로 폴백한다.
2. **타임아웃 분리**: connect 10초 / read 30초. 연결되지 않는 호스트를 60초 기다려도 결과는
   같으므로 지연 손실이 1/6로 줄어든다.
3. **공유 클라이언트**: 커넥션 풀 재사용(max 8) — 핸드셰이크 반복·소켓 고갈 제거.
4. **시간 예산**: `CUSTOMS_TIME_BUDGET_S`(기본 3시간) 초과 시 **수집분을 저장하고 정상 종료**.
   잡 상한은 `timeout-minutes: 240`으로 낮춰, 6시간 강제 취소로 전량 유실되는 일이 없다.
5. **레이트리밋 페이싱**: 호출 간격 1초(기존 0.3초).

예상 소요: 90회 × (응답 2~5초 + 간격 1초) ≈ **10분 이내**.

## 2. Databento — "Response ended prematurely" (A-096)

### 근본원인

`2010-06-06 ~ 2026-08-11`(16년) 전체를 **단일 `get_range` 스트림**으로 요청했다. 이 방식은
스트림이 중간에 끊기면 그때까지 받은 데이터가 **전량 폐기**된다(부분 저장 불가). 응답에 함께
표시된 `(degraded)`는 데이터셋 일부 구간의 원천 품질 상태 안내이며 **차단 사유가 아니다**.

이전 세션의 "종료일을 T-1로 클램프" 방식도 추정치였다 — 라이선스·데이터셋 실제 종료일과
일치한다는 보장이 없어 422를 재발시킬 수 있었다.

### 조치 (API 우선)

1. **실제 가용 구간 조회**: `metadata.get_dataset_range()`로 종료일을 확정 — T-1 추정 폐기.
2. **연 단위 청크**: 17개 요청으로 분할. 한 해가 실패해도 나머지는 보존된다.
3. **청크별 지수 백오프 재시도**(5→10→20초) + **부분 성공 저장**.
4. **상태 사전 로깅**: `metadata.get_dataset_condition()`으로 available/degraded/pending
   일수를 집계 출력. degraded 구간은 수집하되 교차검증 대상으로 표시한다.

`data/raw/Databento` 미생성으로 인한 커밋·아티팩트 경고는 수집 실패의 **결과**이며, 위
수정으로 부분 수집이라도 산출되면 자동 해소된다.

## 3. FAO 요약 — FontBBox 경고 (A-097)

### 근본원인

`Could not get FontBBox from font descriptor because None cannot be parsed as 4 floats`는
pdfplumber의 백엔드인 **pdfminer.six**가 내는 경고로, PDF에 임베딩된 폰트의 **FontBBox
(글리프 경계상자) 항목이 비어 있을 때** 발생한다. 경계상자는 글자 배치 보정에만 쓰이며
문자 코드 추출과 무관하다.

### 무해성 실증

| 지표 | 값 |
|---|---|
| FAO 요약 대상 | 137건 |
| 판독 성공 | **137건 (실패 0)** |
| 평균 추출 문자 수 | 50,893자 |
| 최소 / 최대 | 4,655자 / 193,916자 |

경고가 발생한 실행에서 **텍스트 손실이 전혀 없었음**이 확인된다.

### 조치

`logging.getLogger("pdfminer").setLevel(logging.ERROR)`로 로그 노이즈만 제거. 판독 로직은
변경하지 않는다(오류를 숨기는 것이 아니라, 오류가 아닌 것을 오류처럼 보이지 않게 하는 조치).

## 4. KOSIS·관세청 ConnectTimeout (A-095)

### 현재까지의 진단 이력

| 시도 | 가설 | 결과 |
|---|---|---|
| A-083 | 대륙 간 간헐 지연 | 타임아웃 60초 + 3회 재시도 → 재발 |
| A-085 | 러너 IPv6 경로 블랙홀 | `local_address="0.0.0.0"` IPv4 강제 → **재발** |

두 차례 완화가 듣지 않았다는 것은 **가설이 틀렸을 가능성**을 뜻한다. `httpx.ConnectTimeout`은
DNS 해석·TCP 핸드셰이크·TLS 협상을 한 덩어리로 묶어 보고하므로, 어느 계층이 막혔는지
현재 로그로는 특정할 수 없다.

### 유력 가설 — 장애 1과의 연동

customs-gw 잡이 **1,530회를 6시간 동안 연속 호출**했고, 헬스체크는 그 뒤에 실행됐다.
data.go.kr이 과다 호출 IP를 일시 차단하면 응답 코드가 아니라 **패킷 드롭(=연결 타임아웃)**으로
나타난다. 이는 "직전 실행에서는 셋 다 성공했다"는 간헐성과도 일치한다.

### 조치 (API 우선)

1. **`scripts/diagnose_kr_hosts.py` 신규** — DNS / TCP(80·443) / TLS / HTTP(http·https)를
   **계층별로 분리 측정**. 판정 규칙:
   - DNS 성공 + 전 IP·전 포트 TCP 실패 → 경로 차단 또는 **러너 IP 일시 차단**
   - TCP 성공 + HTTP 타임아웃 → 서버 애플리케이션 지연
   - http 실패 + https 성공 → 평문 80 포트 경로 문제(스킴 전환으로 우회 가능)
2. customs-gw 잡 **선행 스텝으로 진단 배치**(continue-on-error) — 수집 전 상태를 기록.
3. **호출량 17배 감축**(장애 1 조치)으로 차단 유발 요인 자체를 제거.

다음 실행 로그로 계층이 확정되면 스킴 전환·페이싱 조정 중 맞는 대응을 적용한다.
**현시점에서 수동 조치는 불필요**하다.

## 5. USDA PSD 500 (A-098)

### 근본원인

A-076에서 `api.fas.usda.gov` 우선 폴백 체인을 만들었으나 **커넥터에만 적용**했고,
헬스체크 스텝은 구 호스트를 직접 호출하는 코드가 그대로 남아 있었다.

```python
url = "https://apps.fas.usda.gov/OpenData/api/psd/..."   # 구 호스트 직접 호출
r = httpx.get(url, headers={"API_KEY": api_key}, timeout=20)
r.raise_for_status()                                      # 500 → 즉시 예외
```

즉 **500은 서버 문제이자 우리 코드가 이미 알고 있던 이관을 반영하지 않은 문제**였다.

### 조치

호스트 × 인증헤더 조합을 순회한다(ESR 이관 전례 A-019: `X-Api-Key` 헤더 방식).

1. `api.fas.usda.gov` + `X-Api-Key`
2. `api.fas.usda.gov` + `API_KEY`
3. `apps.fas.usda.gov` + `API_KEY` (구 호스트, 최후)

전 후보 실패 시에도 **비치명 처리**한다 — PSD는 수동 업로드 Excel
(`psd_historical.parquet` · 27지표)로 이미 커버되므로 파이프라인 차단 사유가 아니다.

## 6. USDA ARMS 0건 (A-099)

### 근본원인

`api.ers.usda.gov` 신규 스키마는 `{status, info, message, data, detail, errors}` 형태다.
구 코드는 `data`가 비면 **키 목록만 출력하고 assert로 잡을 중단**시켰다. 정작 원인을 담고
있는 `message`·`errors`를 출력하지 않아, 어떤 파라미터가 거부됐는지 알 수 없었다.

### 조치

`message` · `errors` · `detail` · `info` · `status`를 그대로 출력해 다음 실행에서 파라미터를
바로 교정할 수 있게 한다. 동시에 **비치명 처리** — 대두 생산비용은 G1 핵심 8변수에
포함되지 않는 보조 지표다.

## 7. ECMWF CDS "200인데 데이터가 안 보인다" (A-100)

### 조사 결과: 데이터는 수집되지 않았고, 수집될 수도 없었다 — 그러나 문제가 아니다

해당 스텝은 **수집 스텝이 아니라 연결 점검 스텝**이다. 자체적으로 데이터를 저장하지 않는다.
"데이터가 보이지 않는" 것은 정상 동작이다. 다만 스텝 자체에 세 가지 결함이 있었다.

| 결함 | 내용 |
|---|---|
| 이름과 실체 불일치 | 스텝명은 `ECMWF CDS API`인데 실제로는 `archive-api.open-meteo.com`을 호출 |
| 불필요한 인증 | Open-Meteo는 키가 필요 없는데 CDS 인증 헤더를 붙이고, `ECMWF_API_KEY` 미등록 시 점검을 건너뜀 |
| 검증 부재 | `200, 403, 404` 전부를 "연결 정상"으로 출력 — 본문에 관측값이 있는지 확인하지 않음 |

세 번째가 혼선의 직접 원인이다. **연결 성공과 데이터 수신을 구분하지 않았다.**

### 사실관계

- CDS v2 API는 2024년 CDS-Beta 이관으로 폐기됐고, **Nexus는 CDS로 수집한 적이 없다**.
- 기후 데이터의 실제 수집원은 **Open-Meteo ERA5-Land**(`climate_connector.py`, 12개 산지,
  키 불요) — ERA5 재분석이라는 원천 자체는 CDS와 동일하다.

### 조치

스텝을 `Check Open-Meteo ERA5 Archive (기후 실수집원 — CDS 아님)`으로 정정하고,
CDS 키 요구·인증 헤더를 제거했다. 응답 본문의 **일자 수와 실측 기온 개수를 검증**해
`200 + 값 있음`과 `200 + 값 없음`을 구분 출력한다. 이제 "연결됐는데 데이터가 있나"라는
질문에 로그가 직접 답한다.
