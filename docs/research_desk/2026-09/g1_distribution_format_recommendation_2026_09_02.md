# G1 브리프 배포 형식 권고 — HTML+CSS가 어려울 때의 접근

**작성일**: 2026-09-02 · **협의**: MLOps 관점 · 데이터 과학 관점 · **전제**: 통합 후 배포 표면은 Power BI(일
임포트)와 포털(EC2)이며, Apache Hop 배치 체계 안에서 산출된다.

## §1 판정 — 어려운 것은 HTML이 아니다 (CONFIRMED)
현 브리프는 **JS 0 · 인라인 SVG 3종 · CSS 140줄 · 외부 의존은 비차단 폰트 링크 1건**인 단일 HTML 파일이라
정적 호스팅 요건이 극히 낮다(포털 EC2 정적 디렉터리 하나면 됨). 어려움의 실체는 두 가지다: ①Power BI는
HTML을 임포트하지 않는다 ②Hop 배치 체계는 파일 산출물보다 테이블 착지를 전제로 한다. 즉 문제는 **데이터
계약 층이 없다는 것**이며(브리프 생성 함수가 렌더 직전에 데이터를 단일 HTML 문자열로만 내보냄), HTML은
그 계약의 한 표현일 뿐이다.

## §2 권고 — '데이터 계약 우선 · 이중 출력'
1. **데이터 계약 추출**: 브리프 생성 직전에 이미 존재하는 객체(가격 KPI·참고 범위·도착가 범위·상위 변인·경보·
   유사 시기·스냅샷·신호·일정)를 `build_brief_payload()`로 분리 — 순수 리팩터(계산 변경 0).
2. **Mart 테이블 8종**(공통 키 `brief_date, run_id, published_at`, append-only):
   `brief_kpi` · `brief_alerts` · `brief_drivers`(상위 변인·별점·기사 링크) · `brief_analogue`(유사 시기 분포·
   에피소드) · `brief_snapshot`(지표·일간·주간·90일 표준화) · `brief_signals`(비정형 신호·출처) · `brief_calendar`
   (D-day) · `brief_summary`(4단 요약 텍스트 + 신뢰 스트립) + `brief_status` 1행.
3. **Power BI 페이지**가 같은 7블록을 표준 시각화로 재현: 팬 차트=선+영역, 별점=아이콘 열, 유사 시기=표,
   경보=카드, 공급 경로=상태 표(지도는 2단계).
4. **HTML은 부산물**로 유지해 포털 정적 디렉터리(`/daily/{date}.html` + `latest.html`)에 게시 — 변경 0.
5. 어느 표면이 죽어도 **Mart에 데이터가 남는** 구조 → 이관 수용 기준(스냅샷·지표 동등성)의 정박점이 됨.

## §3 대안 비교
| 안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| Power BI 단독 | 사내 권한·배포 체계 재사용, 1차 등재 요건 충족 | 서술형 요약·근거 토글·온톨로지 체인 표현이 약함, 리포트 제작 인력 필요 | 부분 |
| HTML 단독(포털) | 이미 완성, 호스팅 요건 최소, 서술·근거 표현 우수 | Power BI 연동 요건 미충족(1차 등재 실패 위험), 이력 축적·조회 기능 없음 | 부분 |
| **이중 출력(권고)** | 위 둘의 장점 결합, 데이터 계약이 이관·심사·품질 검증의 공통 근거 | payload 리팩터 1.5인일 + Power BI 페이지 제작(사내) | **채택** |

## §5 주의
- 브리프의 하드코딩 2건(WASDE 일정표·파나마/말라카 상태 'ok')은 payload 분리 시 설정 파일로 이동한다.
- PDF 산출(weasyprint)은 **선택 기능**으로 강등 — Power BI·HTML이 정본이면 이관 시 시스템 의존 부담이 사라진다.
- 회사 문서에는 승인자 지시(9/1)대로 호칭은 '최종 결정자/승인자'로 통일하고 코드는 부록에만 둔다.
