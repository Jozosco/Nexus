## ① 수치·단위·논리 오류

- **[높음] 문서 규모 산정이 서로 맞지 않는다.**  
  권장안의 정규화 대상은 `2,175 + 300+ + 66 + 152 = 약 2,693건 이상`인데, 벡터 DB 배제 근거에서는 “문서 ~5천”이라고 한다. 원문 PDF 2,175건까지 별도 문서로 센 경우에만 약 4,868건이 되지만, 제시된 Knowledge Mart 입력에는 원문 PDF가 없고 요약 md만 있다. 어느 단위를 문서로 집계했는지 불명확하다.

- **[높음] 요약 2,175건과 인덱스 2,227행의 52건 차이가 설명되지 않았다.**  
  “원문 PDF와 1:1” 및 “원문↔요약 조인 가능”을 주장하지만, 추가 52행이 원문 없는 레코드인지, 중복인지, 다른 문서 유형인지 제시되지 않았다. 이 상태에서는 1:1 대응과 완전한 조인을 보장할 수 없다.

- **[높음] 제안 스키마로는 EvidenceSpan 계약을 준수할 수 없다.**  
  정규화 필드는 `문서id·유형·날짜·태그·엔티티·본문·출처경로`뿐이며, 계약상 필수라는 `page`와 원문 verbatim span/offset이 없다. 특히 MEMORY와 research_desk, 요약 md의 검색 발췌를 원문 PDF 페이지·인용문과 100% 대조할 경로가 구조에 포함되지 않았다. “준수만 하면 된다”는 결론과 설계가 모순된다.

- **[높음] “FAISS·Chroma·LanceDB = 별도 인프라”라는 분류가 부정확하다.**  
  FAISS는 일반적으로 프로세스 내 라이브러리이며, Chroma와 LanceDB도 로컬 임베디드 형태로 운용할 수 있다. 승인 라이브러리 미등재는 별도의 배제 근거가 될 수 있지만, 세 도구 모두를 외부 인프라 신설과 동일시하는 논리는 성립하지 않는다.

- **[높음] 외부 SaaS의 “잔존자산 0·승계 불가”는 사실상 과도한 단정이다.**  
  Notion과 Airtable은 CSV/Markdown/API 등의 내보내기 경로가 있어 데이터 자산 자체가 0이 되지는 않는다. 계정이나 기능을 그대로 승계하지 못하는 문제와 데이터 이관 가능성을 구분해야 한다.

- **[높음] “비용 0”과 “잔존자산/이식성 100%”의 계산 범위가 잘못됐다.**  
  Phase 1만 해도 반나절의 인건비와 실행 환경·스토리지·테스트 비용이 발생한다. 또한 Parquet 이전만으로 scikit-learn의 TF-IDF 어휘·IDF·희소행렬, 모델 버전, CLI, 권한 및 카탈로그가 Snowflake로 100% 승계되지는 않는다. 이는 서비스 구독료 0과 총비용 0을 혼동한 표현이다.

- **[높음] “단일 parquet + 단일 CLI”만으로 TF-IDF 결과가 재현된다는 주장은 불완전하다.**  
  매 질의마다 TF-IDF를 다시 학습하지 않는다면 vocabulary, IDF, 전처리기 및 희소행렬을 별도로 저장해야 한다. 반대로 매번 학습하면 코퍼스 변경에 따라 동일 질의의 랭킹이 달라진다. 현재 구조에는 어느 방식인지와 필요한 상태 저장이 없다.

- **[높음] Feature Mart의 ASOF JOIN 결정을 Knowledge Mart 검색 방식의 승인 근거로 확장한 것은 논리적 비약이다.**  
  시점 정합 수치 조인을 위해 DuckDB를 선택했다는 결정은 TF-IDF 검색 품질이나 문서 인용 구조의 적합성을 입증하지 않는다. 같은 저장 엔진을 쓴다는 이유만으로 신규 데이터셋·검색 로직에 대한 심의가 불필요하다고 결론낼 수 없다.

- **[높음] 생성과 검색을 분리하면 환각 위험을 “구조적으로 피한다”는 주장은 틀렸다.**  
  에이전트가 검색 결과를 잘못 종합하거나, 미검색 내용을 생성하거나, 낮은 관련도의 문서를 근거로 사용할 위험은 그대로 남는다. 인용 검증·답변 충실도 평가·근거 없는 문장 차단이 없으므로 위험을 회피했다고 볼 수 없다.

- **[참고] 438KB라는 파일 크기만으로 “전문 로드 불가”라고 판단할 수 없다.**  
  바이트 수는 토큰 수가 아니며 인코딩·내용과 사용하는 모델의 컨텍스트 한도에 따라 달라진다. 실제 토큰 수와 로더 제한이 제시되지 않았다.

## ② 시계열 누수 위험

- **[치명] Knowledge Mart에 point-in-time 조회 규칙이 없다.**  
  스키마의 단일 `날짜`가 발행일, 시장 공개일, 실제 입수일, 문서 내 사건일 중 무엇인지 정의되지 않았고 `available_at/ingested_at`도 없다. 역사적 가격 예측이나 백테스트에서 당시에는 존재하지 않았던 GAIN·FAO 보고서, MEMORY 결정, research_desk 사후 정오표가 검색되면 미래정보가 직접 유입된다.

- **[높음] TF-IDF를 전체 코퍼스에 적합한 뒤 날짜 필터를 적용하면 결과 문서를 과거로 제한해도 누수가 남는다.**  
  미래 문서가 vocabulary와 IDF 통계에 영향을 주기 때문이다. 제시된 “DuckDB 메타 필터 + TF-IDF 랭킹”은 필터를 학습 전 적용하는지 명시하지 않는다. 백테스트 cutoff별로 먼저 코퍼스를 제한하지 않으면 랭킹 자체가 미래 코퍼스 정보를 사용한다.

- **[높음] 시맨틱 용어 확장과 MEMORY도 시점 버전이 없다.**  
  현재의 152개 용어·동의어·signal mapping 및 300+ 결정을 과거 질의에 그대로 사용하면, 과거에는 알려지지 않았던 개념·정책 해석·사후 결정이 검색어 확장에 반영될 수 있다. 문서만 날짜 필터링해도 이 누수는 제거되지 않는다.

## ③ 상관을 인과로 과장한 해석

- **[높음] 검색 코드 부재가 반복 조사 비용의 원인이라는 결론에 근거가 없다.**  
  확인된 것은 “의미/랭킹 검색 코드 0건”뿐인데, 이를 근거로 “세션마다 같은 조사를 반복하는 비용이 이미 발생”한다고 단정했다. 세션 로그, 중복 질의 비율, 조사시간 전후 비교가 없으므로 검색 부재와 반복 조사 간 인과관계가 입증되지 않았다.

## ④ 재현 불가능한 주장

- **[높음] “조사 실측” 수치와 코드 0건 판정을 재현할 근거가 없다.**  
  저장소 commit hash, 조사 경로, 제외 규칙, 파일 집계 명령, 중복 판정 방식, CSV 스키마/체크섬, 검색한 코드 패턴이 없다. 따라서 2,175건·2,227행·66건·300+건·152개와 “검색 코드 0건”을 같은 시점 기준으로 재계산할 수 없다.

- **[높음] Phase 2는 임베딩 모델이 특정되지 않아 재현할 수 없다.**  
  `sentence-transformers` 라이브러리명만 있고 HF 모델 ID, revision/commit, 차원, pooling, 정규화, 최대 토큰 길이, chunking 규칙이 없다. 모델 최신 버전이 바뀌면 같은 문서의 벡터와 검색 순위가 달라진다.

- **[높음] “정확한 근거를 빨리 찾는다”는 효능 주장이 평가되지 않았다.**  
  고정 질의 세트, relevance label, Recall@k/MRR/nDCG, 인용 정확도, 지연시간 및 실행 하드웨어가 전혀 없다. 구현도 없는 상태이므로 TF-IDF와 용어 확장이 실제 교차 도메인 질의를 해결한다는 주장을 재현할 수 없다.

- **[높음] Phase별 “~반나절” 산정에 작업량과 측정 기준이 없다.**  
  파서 작성, 청킹, 52행 불일치 처리, EvidenceSpan 검증, 인덱스 갱신, 테스트 및 실패 복구가 견적에 포함됐는지 알 수 없다. 담당자·하드웨어·완료 조건이 없어 같은 공수를 재현할 수 없다.

- **[높음] 외부 제품 배제 근거가 시점·에디션별로 고정되지 않았다.**  
  “NotebookLM은 API도 없음”은 소비자판과 Enterprise 제품을 구분하지 않고, 확인한 공식 문서 URL·버전·확인일도 없다. Azure AI Search 역시 서비스 자체가 GitHub Actions에 본질적으로 종속되는 것은 아니므로, 프로젝트 배포 구조를 보여주는 근거 없이 “Actions 종속 신규”라고 분류한 판정을 재현할 수 없다.
