## ① 수치·단위·논리 오류

- **[높음] 문서 규모 `~5천`의 산정이 제안된 색인 대상과 일치하지 않는다.**  
  구조에 명시된 대상은 `2,175 + 300+ + 66 + 152 = 약 2,693건 이상`이다. 2,227행 인덱스 CSV는 요약 문서의 메타데이터로 설명돼 있으므로 다시 더하면 중복 계상이다. 원문 PDF까지 포함해 약 5천으로 계산했다면, 정규화 구조에는 원문 PDF가 색인 대상으로 기재되어 있지 않다. 따라서 “문서 ~5천이라 벡터 DB가 과잉”이라는 규모 근거가 불명확하다.

- **[높음] FAISS·Chroma·LanceDB를 모두 “별도 인프라/벡터 DB 전용 엔진”으로 분류한 것은 기술적으로 부정확하다.**  
  FAISS는 서버형 DB가 아니라 프로세스 내 라이브러리이고, Chroma와 LanceDB도 로컬·임베디드 구성이 가능하다. 승인 라이브러리 미등재는 별도 배제 근거가 될 수 있지만, “별도 인프라 = D-025 유형”이라는 공통 배제 논리는 성립하지 않는다.

- **[높음] Notion·Airtable 등 외부 SaaS의 `잔존자산 0`, `승계 불가` 단정은 과도하다.**  
  이들 서비스는 일반적으로 CSV·JSON·Markdown 등의 내보내기를 제공한다. 기능·메타데이터의 완전 승계가 어렵다는 주장과 데이터 잔존자산이 0이라는 주장은 다르다. 실제 export/import 시험이나 사내 이관 기준 없이 0%로 판정할 수 없다.

- **[높음] Azure AI Search를 “Actions 종속”으로 규정한 논리가 제시되지 않았다.**  
  Azure AI Search 자체는 API·SDK·포털 등으로 구축·질의할 수 있으며 GitHub Actions에 본질적으로 종속되지 않는다. 프로젝트의 내부 배포 규정 때문에 Actions가 필수라면 해당 규정과 경로를 제시해야 한다.

- **[높음] `비용 0·무료`는 `~반나절`의 개발·검증 노동과 모순된다.**  
  정확한 표현은 “추가 라이선스·서버 비용 0”일 수 있으나 총비용은 0이 아니다. 또한 저장·CI 실행·향후 Blob 사용 비용도 산정에서 빠져 있다.

- **[높음] `parquet 그대로 Blob/Snowflake 승계`, `잔존자산 100%`는 데이터 파일과 검색 기능의 승계를 혼동한다.**  
  설명된 단일 parquet에는 TF-IDF vocabulary·IDF·전처리 설정·질의 확장 규칙·모델 버전이 포함되지 않는다. Phase 2의 sentence-transformers 모델도 parquet에 담기지 않는다. 문서 데이터가 이동 가능하더라도 동일한 검색 결과와 기능이 100% 승계된다고 볼 수 없다.

- **[높음] EvidenceSpan 준수 주장과 제안 스키마가 맞지 않는다.**  
  EvidenceSpan은 `page + 원문 인용`을 강제한다고 했지만, 정규화 스키마에는 문서 ID·유형·날짜·태그·엔티티·본문·출처 경로만 있고 원문 페이지, 원문 인용문, 원문 span 위치가 없다. 요약문 발췌만으로는 “원문 인용 100% 일치”를 보장할 수 없다.

- **[참고] `438KB 문서는 전문 로드 불가`는 바이트 크기만으로 결론 낼 수 없다.**  
  실제 가능 여부는 인코딩, 토큰 수, 사용 모델의 컨텍스트 한도와 에이전트 입력 예산에 달려 있다. 적용 모델과 토큰 실측 없이 절대적인 “불가” 판정은 성립하지 않는다.

- **[참고] `Phase 1→2는 같은 스키마라 재작업 없음`은 로드맵 자체와 충돌한다.**  
  Phase 2에는 임베딩 컬럼, 차원·모델·revision·정규화 방식 등의 메타데이터가 추가되어야 하며 전체 문서 재임베딩도 필요하다. 최소한 스키마 변경과 인덱스 재빌드는 발생한다.

## ② 시계열 누수 위험

- **[높음] Knowledge Mart에 필수 `as_of`/`available_at` 통제가 없다.**  
  문서 날짜만 저장하며, 예측 기준시점에 실제 이용 가능했던 시각·수집 시각·개정 시각을 구분하지 않는다. 과거 예측이나 백테스트에서 이후 작성된 MEMORY 결정, research_desk 정오표, 사후 요약을 검색하면 미래 정보가 직접 유입된다.

- **[높음] 메타데이터 필터와 TF-IDF 학습·랭킹의 순서가 명시되지 않았다.**  
  결과 문서만 날짜로 걸러도 TF-IDF vocabulary와 IDF를 전체 기간 말뭉치로 적합하면 미래 문서의 단어 분포가 과거 시점 랭킹에 반영된다. 예측 시점별로 먼저 `available_at <= cutoff`을 적용한 뒤 vectorizer를 적합하거나, 고정 학습 시점의 인덱스를 버전 관리해야 한다.

- **[높음] 요약·태그·엔티티·감성·시맨틱 용어의 생성 시점과 버전이 없다.**  
  원문은 과거 문서여도 태그나 요약이 이후 자료·온톨로지·모델로 생성되었다면 백테스트 시 미래 지식이 섞일 수 있다. 원문 발행일 외에 파생물 생성 시각, 생성 모델·버전, 적용 가능 시작일이 필요하다.

## ③ 상관을 인과로 과장한 해석

- **[높음] “생성 층과 검색 층의 분리가 환각 리스크를 구조적으로 피한다”는 인과적 단정이 잘못됐다.**  
  계층 분리는 환각을 줄일 수 있는 설계 요소일 뿐이다. 생성 에이전트가 검색 근거를 왜곡하거나, 잘못된 문서를 인용하거나, 근거 밖 내용을 생성할 위험은 그대로 남는다. 인용 정확도·근거 충실도 평가 없이 “구조적으로 피한다”고 할 수 없다.

- **[참고] 의미 검색 부재가 반복 조사 비용의 원인이라는 주장이 측정 없이 제시됐다.**  
  “세션마다 같은 조사를 반복”하는 현상이 있더라도 원인이 검색 기능 부재인지, 기록 절차 미준수·문서 품질·에이전트 프롬프트 문제인지 분리되지 않았다. 질의 로그, 중복 조사율, 검색 도입 전후 비교가 필요하다.

## ④ 재현 불가능한 주장

- **[높음] `조사 실측` 수치의 재현 절차가 없다.**  
  저장소 commit, 조사 시각, 포함·제외 경로, glob, 심볼릭 링크·중복 처리, 바이트 단위 기준, 실행 명령과 출력이 없다. 특히 2,175개 요약과 2,227개 인덱스 행에 대해 orphan·중복·anti-join 결과가 없어 “원문↔요약↔메타데이터가 한 테이블로 조인 가능”을 검증할 수 없다.

- **[높음] 검색 결과를 재현할 핵심 사양이 누락됐다.**  
  문서/청크 단위, Markdown 정규화, 언어별 토큰화, `TfidfVectorizer` 파라미터, 질의 확장 순서, 필터 적용 순서, 점수 결합식, 동점 처리, 라이브러리 버전과 corpus snapshot이 없다. 같은 문서 집합으로도 상위 N 결과가 달라질 수 있다.

- **[높음] Phase 2 임베딩은 모델 식별 정보가 없어 재현할 수 없다.**  
  `sentence-transformers`는 라이브러리명일 뿐이다. 정확한 모델 ID, Hugging Face revision/commit, 차원, pooling, 정규화, 최대 토큰 길이, 라이선스와 모델 파일 해시가 필요하다.

- **[참고] `~반나절` 일정은 작업 분해와 측정 근거가 없다.**  
  카탈로그 파싱, 중복·오류 처리, EvidenceSpan 검증, 테스트, 성능 측정, 문서화 범위 및 실행 환경이 제시되지 않아 다른 작업자가 재현 가능한 견적이 아니다.

- **[참고] 외부·내부 정책 사실의 확인 가능한 근거가 부족하다.**  
  NotebookLM API 부재, 승인 라이브러리 목록, egress allowlist, D-025/D-026/D-028 등의 결론에 대해 정확한 파일 경로·버전·인용문 또는 외부 URL과 확인일이 없다. 보고서만으로는 해당 판정의 유효성을 독립 검증할 수 없다.
