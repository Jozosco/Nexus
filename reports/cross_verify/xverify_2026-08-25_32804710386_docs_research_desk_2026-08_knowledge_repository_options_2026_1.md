## ① 수치·단위·논리 오류

- **[높음] 요약과 인덱스의 건수가 불일치하며 조인 완전성이 입증되지 않았다.**  
  요약은 2,175건인데 인덱스는 2,227행으로 **52행 차이**가 난다. 고유키, 중복·결측 수, 1:1/1:N 관계를 제시하지 않은 상태에서 “원문↔요약을 한 테이블로 조인 가능”, “원문 PDF와 1:1”이라고 단정했다. 이 차이는 잘못된 근거 연결이나 중복 검색을 유발할 수 있다.

- **[높음] “문서 약 5천”이라는 규모 산정의 단위가 일관되지 않는다.**  
  Knowledge Mart 입력으로 명시한 항목은 `2,175 + 300+ + 66 + 152 ≈ 2,693+` 레코드다. 원문 PDF 2,175건까지 별도 문서로 중복 계산해야 약 4,868건이 되지만, 구조도에는 PDF 본문이 입력 대상으로 표시되지 않았다. 문서·결정·용어·인덱스 행을 혼합한 규모로 벡터 검색 방식을 배제하고 있다.

- **[높음] FAISS·Chroma·LanceDB를 모두 “벡터 DB 전용 엔진·별도 인프라”로 묶은 것은 기술 분류 오류다.**  
  FAISS는 서버가 필수인 DB가 아니라 프로세스 내에서 사용할 수 있는 검색 라이브러리이고, Chroma/LanceDB도 로컬·임베디드 구성이 가능하다. 승인 라이브러리 목록에 없다는 사유와 “별도 인프라”라는 사유는 구분해야 한다.

- **[높음] 외부 SaaS의 “잔존자산 0·승계 불가” 결론이 전제에서 도출되지 않는다.**  
  SaaS 계정 자체를 승계하지 못하더라도 데이터의 CSV·Markdown·API export 가능성은 별도 검토 대상이다. 다른 시스템에 대한 D-025 논리를 Notion·Airtable에 그대로 적용했을 뿐, export 형식·첨부파일·메타데이터 보존율을 측정하지 않았다.

- **[높음] EvidenceSpan 준수를 강제한다는 주장과 제시된 스키마가 모순된다.**  
  저장 필드는 문서 ID·유형·날짜·태그·엔티티·본문·출처 경로뿐이다. 필수라고 한 **원문 페이지, 원문 인용문, span offset, 원문 문서 ID**가 없다. 검색 결과의 요약문 발췌만으로는 “page+원문 인용 100% 일치”를 구조적으로 검증할 수 없다.

- **[높음] “Phase 1→2는 같은 스키마라 재작업 없음”은 로드맵 자체와 충돌한다.**  
  Phase 2에서 임베딩 컬럼을 추가하려면 모델 ID·revision·차원·dtype·정규화 방식·청크 ID 등의 스키마와 메타데이터가 필요하다. 이 필드가 Phase 1 설계에 없으므로 최소한 스키마 변경과 전체 재빌드가 필요하다.

- **[높음] “비용 0·무료”는 비용 범위를 잘못 표시했다.**  
  Phase 1·2 각각 반나절의 인건비가 명시되어 있고, Phase 2에는 모델 다운로드, 계산 자원, 저장공간 및 egress가 필요하다. 정확한 표현은 “추가 라이선스·관리형 서비스 비용 0”일 수 있으나 총비용 0은 아니다.

- **[높음] “parquet 전량 승계·잔존자산 100%”는 저장 데이터와 검색 시스템을 혼동한다.**  
  parquet만으로는 TF-IDF vocabulary/IDF, tokenizer 설정, 의존성 버전, 임베딩 모델 및 revision, CLI 동작 환경이 승계되지 않는다. Blob에 파일을 복사하거나 Snowflake가 parquet를 읽을 수 있다는 사실만으로 검색 동작까지 100% 승계되는 것은 아니다.

- **[높음] 검색과 생성을 분리하면 환각을 “구조적으로 피한다”는 결론은 성립하지 않는다.**  
  에이전트가 검색 결과와 다른 내용을 생성하거나, 여러 문서를 잘못 종합하거나, 인용문보다 강한 결론을 낼 수 있다. claim-to-span entailment 검사나 인용 강제 검증기가 설계되어 있지 않다.

- **[참고] “438KB 문서는 전문 로드 불가”는 단위가 부적절하다.**  
  로드 가능 여부는 바이트가 아니라 토큰 수, 인코딩, 모델 context window, 시스템 프롬프트 점유량으로 판단해야 한다. 해당 문서의 토큰 수와 사용 모델 한도가 없어 불가 판정을 재현할 수 없다.

- **[참고] 한국어 질의 예시와 TF-IDF 검색의 언어 정합성이 설명되지 않았다.**  
  예시는 한국어지만 GAIN·FAO 요약 본문의 언어와 한↔영 용어 매핑 범위가 제시되지 않았다. 본문이 영어 또는 혼합 언어라면 기본 TF-IDF는 언어 간 의미 대응을 하지 못하므로 제시한 질의가 작동한다는 논리가 성립하지 않는다.

## ② 시계열 누수 위험

- **[치명] 시점 정합 저장소라고 설명하면서 point-in-time 통제가 전혀 없다.**  
  스키마에는 모호한 `날짜` 하나만 있고, 원문 발행시각·최초 입수시각·요약 생성시각·수정시각·`available_from`·`as_of`가 없다. CLI에도 기준시점 인자가 없다. 과거 예측이나 백테스트에서 이후 발행된 보고서, 정오표, MEMORY 결정을 검색하면 미래정보가 직접 유입되어 평가가 무효화된다.

- **[높음] 결과 문서만 날짜 필터링해도 전체 코퍼스로 TF-IDF를 학습하면 누수가 남는다.**  
  미래 문서가 vocabulary와 IDF(문서 빈도)를 바꾸므로 과거 시점의 검색 순위가 당시에는 알 수 없던 미래 코퍼스 분포에 의존한다. `as_of` 기준으로 문서를 먼저 제한한 뒤 vectorizer를 적합하거나 시점별 인덱스를 고정해야 한다.

- **[높음] 현재 시점의 용어·태그·감성·인과엣지를 과거 검색에 재사용하는 경로가 열려 있다.**  
  152개 용어와 21개 인과엣지의 생성·유효 시점 및 버전이 없다. 이후에 확립된 동의어, 사건 분류, 감성 또는 관계가 과거 질의를 확장하면 문서 자체를 날짜로 제한해도 미래 지식이 검색 과정에 주입된다.

## ③ 상관을 인과로 과장한 해석

- **[높음] 21건을 “인과엣지”로 명명했지만 인과 식별 기준이 없다.**  
  시간적 선후, 교란 통제, 자연실험·도구변수·구조모형 등의 기준이 제시되지 않았다. EvidenceSpan은 출처가 특정 문장을 말했다는 사실만 보장하며 그 관계의 인과성을 입증하지 않는다. 이 엣지를 질의 확장에 사용하면 출처의 주장이나 단순 동행 관계가 확정적 인과관계로 재생산될 수 있다.

- **[참고] 검색 경로 부재가 반복 조사 비용을 발생시킨다는 설명에 측정 근거가 없다.**  
  “세션마다 같은 조사를 반복하는 비용이 이미 발생”했다고 했지만 세션 로그, 중복 질의율, 조사시간 비교가 없다. 반복 조사의 원인이 검색 부재인지 업무 절차·문서 품질·에이전트 지시 문제인지 분리되지 않았다.

- **[높음] “조사 실측” 수치를 재생성할 방법이 없다.**

  문서/청크 경계, Markdown 정제, Unicode 정규화, tokenizer, stopword, n-gram, `min_df`·`max_df`, sublinear TF, tie-break, 메타 필터 적용 순서, scikit-learn 버전이 빠져 있다. 같은 parquet를 사용해도 검색 순위가 달라질 수 있다.

- **[높음] “정확한 근거를 빨리 찾는다”는 품질·성능 주장이 검증되지 않았다.**

- **[높음] Phase 2 임베딩 검색은 모델이 특정되지 않아 재현할 수 없다.**  
  `sentence-transformers` 패키지만 지정했고 모델명, Hugging Face revision/hash, 라이선스, 다국어 지원 여부, pooling·정규화 방식, 유사도 함수가 없다. 특히 한국어 질의 예시를 지원하는지 검증할 수 없다.

  대상 레코드 수와 청크 수, 파서 예외 처리, 테스트·문서화·CI·EvidenceSpan 검증 범위, 담당자 숙련도와 하드웨어가 제시되지 않아 일정 추정을 재현할 수 없다.
